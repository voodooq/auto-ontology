# 可信查询与答案校验（Grounded query and answer validation）

> 本文档为 [`skills/nvidia-ontology-query/references/query-validation.md`](../../../../../skills/nvidia-ontology-query/references/query-validation.md) 的简体中文翻译版。

在执行完父技能中的常规 MCP 或 REST 就绪检查与可回答性检查之后，使用本工作流处理描述性与诊断性提问。本流程分别对生成的 SQL、返回的数据行和最终回答文本进行独立核验；**仅凭 SQL 执行成功并不足以证明回答了用户的真实意图。**

## 厘清实质问题边界

调用 `ask_question` 之前，先明确并重述以下约束条件：

- 统计总体（Population）与排除范围；
- 指标（Measure）、物理单位与结果粒度（Grain）；
- 分组、排序与去重规则；
- 时间范围、数据截止时间（As-of time）与对比基准；
- 运行批次/场景标识、父级血缘、状态、有效期与替代关系；
- 所需的数据源或产物角色。

当存在实质性业务歧义时，应先向用户澄清，切勿擅自挑选一个看似方便的默认口径。务必锁定经批准的业务术语（Term）、SQL 属性、源表达式、分母、过滤条件及 Join 路径，不要用名称相近的其他指标或源字段替代。

## 审查生成的 SQL

核查生成的 SQL 是否完整保留了所有实质约束，重点关注：

- 必需的表、列、Join、字面值条件与时间谓词是否均已包含；
- Join 是否使用了经批准的连接键与方向；
- 明细行是否已先在明细粒度聚合后再关联运行汇总表；
- 已经是运行级别（Run-level）的指标，是否错误地在与一对多明细表 Join 后再次被 `SUM` 累加；
- 数量（Quantity）是否被误替换为比率、速率、平均值或区间总计；
- 请求的批次（run）、场景（scenario）、父级（parent）、状态、有效期与替代过滤条件是否显式写入；
- 所选用的哈希值或标识符是否对应所请求的源角色。

如果遗漏或替换了任何实质约束，**切勿将该结果当作有效答案呈现**。请保留该 SQL 并明确指出不匹配之处，或请求澄清。一旦检测到一对多扇出放大（Fanout），必须重新获取并执行修正为正确运行粒度的查询，再呈现已校验结果。诊断放大问题时可将某运行级数值作为源证据参考，但绝不能将其重新贴标为经查询校验的结果。

## 独立核验返回行

核对返回行中的主键、统计总体、基数、数值、单位、时间范围、分母、血缘以及字面状态值。当返回行允许时，自行重算简单的加总与比率。**空结果或 NULL 并不自动等价于 0。**

**被截断的结果集不能用来证明完整列表、全量排名或总计。** 应当收窄断言范围，或发起覆盖全量总体的聚合查询。同时注意将原始精确数值与展示层的四舍五入值区分开。

## 核验最终回答文本

回答应直接围绕返回数据行中的事实展开，而不是复述 SQL 的逻辑步骤。确保自然语言描述与已验证的数值、单位、统计范围与状态严格一致，并在需要时保留精确标识符与字面推荐状态。

严格区分已观测（observed）、已计算（computed）、建模得出（modeled）、预测（predicted）、推荐（recommended）与已承诺（committed）这几类不同性质的证据状态。检索到一条“推荐建议”并不等于该操作已被批准或执行。诊断性相关性也不等于因果关系；反事实断言必须具备相应的因果证据支撑。

## 多轮追问与失败处理

在进行多轮对话追问前，务必等待上一轮 SSE 流返回 `[DONE]`，并保留关键约束条件。针对相互独立的评估问题，请使用全新的会话线程；严禁将预期答案或评测标准答案（Gold answer）放入模型上下文。

留存一份简明回执，记录：问题标识、本体/源标识、SQL、返回行、行数、截断标记、回答文本、尝试次数及发现的能力缺口。**切勿记录任何凭据。** 当遇到证据缺失、统计总体错误、状态无效或无法核实的截断时，请按“失败关闭（Fail Closed）”原则拒答并如实说明，切勿静默裁剪或擅自取最新一行凑数。
